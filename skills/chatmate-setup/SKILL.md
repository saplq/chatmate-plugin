# Set up ChatMate

Run this setup after installation in the current Work chat. Explain the necessary installation and Telegram sign-in confirmations in the user's language. Never ask for credentials in chat. Use one active executor; no automatic provider fallback.

Set up ChatMate for tasks I write to my private ChatMate bot. Use this Work chat as the only active executor. If ChatMate is not installed, help me install the ChatMate plugin available to this account. If it is unavailable, explain that I need access to the plugin first; do not claim installation from an arbitrary repository is supported in ChatGPT. If it is not connected, open its connection flow (manual fallback: https://chatgpt.com/settings/plugins-settings, ChatMate, Connect). Wait while I confirm installation, sign in with Telegram and click Allow. Never ask me to paste credentials or tokens into this conversation.

Call get_connection_status and list_chats. Identify my owner_private bot chat from the returned data. In ChatGPT Work on the web, or desktop Work with Cloud selected, subscribe to owner.message.created and approval.resolved for that bot chat using ChatMate's MCP Events. Confirm monitoring only after the subscription succeeds. Recheck get_connection_status: automation.status must be needs_test or ready. Ask me to send one short task to my private bot; claim it and return the answer there. Report setup complete only when automation.status is ready. Do not use a manual answer or OAuth alone as evidence of automatic execution. If this surface has no Events, explain that ordinary MCP access does not run tasks automatically; offer manual use here. Do not enable another executor or claim automatic Claude fallback.

For each new owner task, use data.message_id (the canonical ChatMate UUID), create one execution_id UUID and keep it on retries. Call begin_answer before doing work. Continue only if this execution owns the answer; if another execution owns it or the task is stopped, expired or complete, do not act or send a second answer. Save the returned answer_id and include both answer_id and the same execution_id on every send_message, send_to_chat, request_approval and telegram_action call for this claimed task. The server validates the pair and Stop blocks task actions that have not started; never omit the pair to bypass Stop. Standalone actions outside a claimed task omit both. Read get_message_context, follow accessible reply parents and relevant attachments, then use my available tools to do the task. Call update_answer with an increasing sequence and a phase: thinking, reading_conversation, checking_document or preparing_answer; optionally send accumulated answer text, at most 4000 characters. My explicit request authorizes that exact Telegram action and recipient. Clarify essential ambiguity or changed scope; request_approval is optional when I want confirmation in Telegram. Honor native client permissions and other connectors’ rules. Finish with finish_answer using the answer_id, the same execution_id, final text and one stable idempotency_key UUID. Check answer_status before reporting delivery; pending is not sent, and unknown must not be sent again. If I stop generation, stop this task and its new actions. Tell me which bot chat and executor are configured, and what still needs a manual step.

For approval.resolved, call get_approval_status and resume only the already described action if approved. Do not treat it as a new owner task or call begin_answer without a message UUID. If Events or owner answer tools are unavailable, state the limitation and leave manual retrieval available. Do not claim a successful automatic setup until the bot test is delivered and get_connection_status reports automation.status=ready.
